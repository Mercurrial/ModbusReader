# Участие в разработке

Спасибо за интерес к ModbusReader. Ниже описано, как сообщить об ошибке,
предложить улучшение, поделиться картой регистров прибора и прислать изменения
в коде.

## Сообщения об ошибках

Перед созданием задачи проверьте, нет ли уже такой среди
[открытых](https://github.com/Mercurrial/ModbusReader/issues). Новую задачу
создавайте по шаблону «Сообщение об ошибке» и укажите:

- версию программы («О программе») и способ установки (установщик или
  портативный exe);
- версию Windows и модель адаптера RS-485;
- параметры связи (скорость, чётность, стоп-биты, адрес прибора);
- шаги, которые приводят к ошибке, ожидаемый и фактический результат;
- файл `modbusreader_errors.log`, если он есть (лежит рядом с файлом
  настроек — путь указан в «О программе»), и при необходимости снимок экрана.

Если ошибка связана с конкретной картой регистров или проектом, приложите
файл `.json` или `.mbproj`. Не публикуйте сведения, которые нельзя раскрывать.

О проблемах безопасности не пишите в открытые задачи — порядок описан в
[SECURITY.md](SECURITY.md).

## Предложения

Опишите задачу, которую нужно решить, а не только желаемую кнопку: так проще
найти решение, подходящее для всех. Используйте шаблон «Предложение».

## Карты регистров приборов

Карты распространённых приборов полезны другим пользователям. Пришлите карту
(`.json` из редактора карты или `.mbproj`) через шаблон «Карта регистров»,
указав производителя, модель и версию прошивки, на которой карта проверена.

## Изменения в коде

### Окружение

Нужен Python 3.10 или новее (разработка ведётся на 3.12) и Windows; ядро и
большая часть интерфейса работают и на Linux.

```bash
python -m venv .venv
.venv\Scripts\pip install -r requirements.txt
.venv\Scripts\python main.py
```

Перед началом работы прочтите [ARCHITECTURE.md](ARCHITECTURE.md): в нём
описаны устройство кода, точки расширения и правила, которые нельзя нарушать.

### Тесты

```bash
.venv\Scripts\python -m pytest
```

Тесты выполняются без экрана. Любое изменение поведения сопровождается тестом;
исправление ошибки — тестом, который без исправления не проходит. Проверяйте
реальный путь пользователя (события мыши и клавиатуры, настоящие диалоги), а не
только обработчики. Тесты не должны обращаться к реальным настройкам, папке
«Документы» и сети.

Изменения интерфейса удобно проверять снимками экрана:
`python tools/ui_snapshots.py <папка>` отрисовывает все экраны, меню и
диалоги без открытия окна.

### Стиль

- Код пишется в стиле окружающего: те же имена, идиомы и плотность
  комментариев. Комментарий объясняет, *почему* код устроен именно так.
- Новые возможности добавляются через существующие реестры (типы данных,
  настройки, команды, виджеты дашборда) — см. раздел «Extension points» в
  ARCHITECTURE.md.
- Все тексты интерфейса — в `app/i18n.py`, на русском и английском. Цвета —
  только токены темы; значки — только из `gui/icons.py`, без эмодзи.
- Порядок байт по умолчанию (SHORT `AB`, LONG `ABCD`, FLOAT `BADC`) не
  меняется.

### Коммиты и pull request

- Один коммит — одно изменение. Сообщение начинается с типа: `feat:`,
  `fix:`, `ui:`, `refactor:`, `docs:`, `tools:`; первая строка — кратко, что
  изменилось, ниже — зачем.
- Каждый коммит проходит тесты.
- В описании pull request укажите, что и зачем изменено, как это проверено, и
  приложите снимки экрана «до» и «после» для изменений интерфейса.
- Заметное для пользователя изменение добавьте в раздел «Не выпущено» файла
  [CHANGELOG.md](CHANGELOG.md).

Выпуски, номера версий и сборку выполняет сопровождающий
(`tools/release.py`, `tools/build_installer.py`).
